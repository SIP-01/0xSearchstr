# Security Audit — SIP-01/0xSearchstr — 2026-10-20

## Summary

Nostr search engine with a serious backend: Meilisearch + Nostr crawler + clearnet/Tor/I2P crawlers + NIP-50 relay + abuse-report API (docker-compose stack) and a React SPA reading SIP-01 kind 39697 observations. **This repo still carries the full set of vulnerabilities that its own ecosystem fork (0xPresearchstr PR #2, merged 2026-10-14, documented in that repo's `docs/CODE-REVIEW.md`) found and fixed** — plus dangerous default credentials in docker-compose that turn a zero-config deployment into a remotely administrable index. Frontend SPA is otherwise careful (CSP, URL sanitization, no dangerouslySetInnerHTML) and SECURITY.md exists.

**Counts: 2 CRITICAL / 3 HIGH / 3 MEDIUM / 2 LOW**

## Findings

| ID | Severity | File/Area | Issue | Recommended fix |
|----|----------|-----------|-------|-----------------|
| SRCH-1 | CRITICAL | `docker-compose.yml` (meilisearch) | `MEILI_MASTER_KEY: ${MEILI_API_KEY:-change-me}` — if `.env` is not configured, Meilisearch runs with the publicly known master key `change-me` **and port 7700 is published on the host**. Anyone who can reach the host gets full read/write/**delete** over the search index | No insecure default: fail startup when `MEILI_API_KEY` is unset (`${MEILI_API_KEY:?required}`); bind 7700 to the internal network only (drop `ports:`) |
| SRCH-2 | CRITICAL | `docker-compose.yml` + `backend/abuse-api/src/index.ts` | `ABUSE_ADMIN_TOKEN: ${ABUSE_ADMIN_TOKEN:-change-me}` — compose injects the known constant `change-me` when unset, which *enables* the admin API (`isAdmin` only fails-closed when the token is empty). Admin endpoints can list reports and **delete arbitrary documents from the index** by URL hash | Remove the `:-change-me` fallback so empty token = admin disabled; generate a random token in docs |
| SRCH-3 | HIGH | `backend/clearnet-crawler/src/index.ts` | **SSRF**: crawler fetches arbitrary URLs and follows redirects with no private/loopback/link-local IP check (no `backend/shared/src/public-fetch.ts` in this repo — confirmed absent). A hostile page can redirect the crawler to internal services; fetched HTML can enter the public index | Backport the fork's fix: `public-fetch.ts` (BlockList for private ranges, DNS-pinning, re-check every redirect incl. robots.txt/sitemaps, byte-limited reads) |
| SRCH-4 | HIGH | `backend/nip50-relay/src/index.ts` | Unauthenticated remote crash: `['REQ','x',null]` reaches `filter.search` outside the try block and the rejected promise is unhandled → process exit (no `isNostrFilter` validation — confirmed absent). One WS message takes search down for all users | Backport the fork's fix: structural filter validation, sub-id/limits caps, `maxPayload`, catch handler rejections |
| SRCH-5 | HIGH | `backend/abuse-api/src/index.ts` | `Access-Control-Allow-Origin: *` on **all** endpoints including admin (`GET /api/reports`, `PATCH /api/reports/:id`). Bearer-token auth limits direct exploitability, but any web page can drive the API from a browser where the token is reachable, and it trains bad cross-origin expectations | Restrict CORS to the deployed frontend origin; drop `*` at least on admin routes |
| SRCH-6 | MEDIUM | `backend/abuse-api/src/index.ts` (`handleSearch`), `backend/nip50-relay/src/index.ts` | Meilisearch filter injection: user-controlled `source`/`kind` (abuse-api) and `authors`/`#t` values (relay) are string-interpolated into filter expressions — crafted quotes/expressions alter the query | Use `JSON.stringify()` quoting / numeric validation (as the fork now does) |
| SRCH-7 | MEDIUM | `backend/abuse-api/src/index.ts` (`handleReviewReport`) | Report marked `removed` and persisted even when Meilisearch deletion fails — moderator gets false confirmation while content stays indexed (fixed in fork) | Persist `removed` only after the deletion task succeeds; return retryable 5xx otherwise |
| SRCH-8 | MEDIUM | `src/lib/providers/web-index.ts` | Observation integrity check runs **after** grouping, only on the selected latest event: an attacker-signed event squatting a victim's `d` tag with mismatched `u` gets rejected *after* it displaced the valid event → legitimate pages vanish from results (fixed in fork: verify every observation before grouping) | Backport: `verifyObservation()` on every observation before `groupByDocument` |
| SRCH-9 | LOW | `backend/nostr-crawler/src/index.ts` | Ingest trusts relay-supplied events (sub kinds 0/1/1063/30023); no client-side kind/signature re-check beyond library defaults | Verify kind against the subscription filter and (if not delegated to nostrify) `verifyEvent` before indexing |
| SRCH-10 | LOW | `docker-compose.yml` | Unpinned `:latest` third-party images (`dperson/torproxy`, `purplei2p/i2pd`); Tor SOCKS 9050 + i2pd console 7070 published on the host | Pin image digests; don't publish proxy/console ports externally |

## Secrets Check

- GHAS secret scanning not enabled (org-wide gap); compensated with org code searches (`nsec1`, `sk-`, `xai-`, `pkm_`, `api_key`, `PRIVATE KEY`, bearer): only placeholders (`your-meilisearch-master-key-change-this` in `.env.example`) and test values. **No live secrets committed.**
- The `change-me` strings above are not leaked operator secrets — they are *dangerous defaults*, reported as CRITICAL misconfiguration.

Backend deps current (meilisearch ^0.44, ws ^8.18, pino ^9, cheerio ^1, nostr-tools ^2.23, tsx ^4.19). Frontend stack modern. No git-URL deps. No CVE claims without justification.

Treat that PR as the backport source.
